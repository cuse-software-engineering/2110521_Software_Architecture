####################  1. What we demo

Flows (2)
- Create Zone Map + Create Round          (UC-04, UC-03: Manager, back-office)
- Create Booking (hold a table)           (UC-01 steps 3-11: Customer)

Services (3)
- API Gateway                = the only REST API: the REST CRUD of the brief is its routes on zone maps and rounds,
                               each route one gRPC call to the owning service (ADR-12)
- Concert Round Service      = gRPC: zone maps, rounds, table types, parameters (CRUD); called by the gateway and Booking
- Booking Service            = gRPC: customer flow (caller in metadata) + gRPC client of the two others
- Table Availability Service = the gRPC service with CRUD   (round table status: create = C, get = R,
                               hold / release / book = U, remove = D). Called by the other two and by the gateway (polled read).

CRUD needs a delete, the use cases have none -> add two small functions and record them in the document (CH-40):
- Concert Round Service: discardDraftRound(), discardDraftZoneMap()
- Table Availability Service: removeRoundTableStatus() (when a draft round is discarded)

Stubs for progress 1 (say so in the doc, section "implementation status")
- Fake auth: gateway trusts a header (x-user = customer LINE id or staff account, x-role) — no LINE Login, no JWT yet
- No payment, no notification, no staff-account service yet (Booking stops at "held" with party size + fee)
- Storage: MongoDB per service in docker-compose (Mongoose model = the schema, ADR-06). In-memory Map only as a
  fallback if Mongo costs time. No ER diagram: the Mongoose models are the schema.
