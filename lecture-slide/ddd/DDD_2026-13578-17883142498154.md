## Slide 20 — Layered Architecture

![Slide 20](png/page-20.png)

A common architectural solution for domain-driven designs contain **four** conceptual layers (diagram of four columns of boxes with dependency arrows flowing from left to right):

- **User Interface**
- **Application** — Coordinates tasks and delegates work to collaboration of domain objects in the domain layer
- **Domain (Model layer)** — Represents concepts of the business. The heart of the software; the domain model lives — entities, value objects, aggregates, domain services, and business rules.
- **Infrastructure** — Provides generic technical capabilities that support higher layers, e.g., message sending, persistence for the domain, drawing widgets

## Slide 21 — Entities

- An **Entity** is an object defined primarily by **its identity**, not by its attributes. Two entities with identical attribute values are still different objects if their identities differ.
- That identity **persists across the entire lifecycle** of the object — even as its attributes change over time, it remains "the same thing." e.g., `Plane` is still the same plane after a repaint, an engine swap, or a change in route
- Because **identity — not current state** — is what matters, entities are usually given an explicit, stable identifier (e.g., a plane's tail number, a flight plan's flight number) so the system can track and distinguish them reliably, even across restarts, database saves, and updates.
- Examples: Plane, Flight plan, Route, Fix, Airport

## Slide 22 — Value Objects

- A **Value Object** describes some aspect or characteristic of the domain, and — unlike an Entity — it has no identity of its own.
- Two value objects with the same attributes are considered interchangeable and equal. For example, two Money objects both representing "$50 USD" are simply the same value.
- Rule of thumb for modeling: default to Value Objects. Only promote an object to an Entity if it truly needs a persistent identity that must be tracked across state changes.
- Value Objects should be immutable. Rather than modifying a Value Object's internal state, you create a new instance with the desired values and replace the old one.

## Slide 23 — Value Objects (Example)

- Examples (Air travel booking system): The flight code (e.g., "AA123") is a Value Object — it has no identity of its own and can be safely shared across many customers who book the same flight.
- A customer's booking, by contrast, is not a Value Object — it's an Entity, since it gets its own booking reference that persists across changes (seat reassignment, cancellation, rebooking), even if two bookings share the same flight code.
- Contrast with Entities: where an Airport, Plane, or Booking needs a stable identity tracked over time (an Entity), a FlightCode or Fare is just a descriptive value attached to that entity — replaceable and comparison-by-value only.

## Slide 24 — Is "Address" a Value Object?

**It depends on context.**

There's no universal answer — the same real-world concept (Address) can be modeled differently depending on what the software actually needs to do with it. This is a direct consequence of the Ubiquitous Language being tied to a specific bounded context.

## Slide 25 — Is "Address" a Value Object? (Mail-Order Company)

**Mail-order company → Address is a Value Object**

- The address is only needed to confirm the credit card and route the parcel.
- It doesn't matter whose address it is or whether two customers share the same location (e.g., roommates).
- Since identity is irrelevant and only the attribute values (street, city, zip) matter, it's modeled as a Value Object.

## Slide 26 — Is "Address" a Value Object? (Postal Service)

**Postal service → Address is an Entity**

- The system organizes delivery routes using a hierarchy: regions → cities → postal zones → blocks → individual addresses.
- Each address derives its zip code from its position in that hierarchy.
- If the postal service reorganizes postal zones, an address needs to persist its identity and "come along for the ride" as its attributes (like zip code) change.
- Since the address must be tracked and updated over time while remaining "the same address," it qualifies as an Entity.

## Slide 27 — Is "Address" a Value Object? (Electric Utility Company)

- **Electric utility company → Address is an Entity** (with an alternative modeling option)
- An address represents a specific service destination — the company needs to know exactly which physical location is receiving power, even if multiple customers (e.g., roommates) share that address.
- Because the company must track and distinguish that specific service destination over time, Address becomes an Entity.

## Slide 28 — Is "Address" a Value Object? (Alternative Model)

- Alternative model: instead of making Address an Entity, the company could introduce a new Entity called **Dwelling** (the actual place receiving service) and attach Address to it merely as a descriptive attribute. In that case, Address reverts to being a Value Object, and Dwelling — not Address — carries the identity.

## Slide 29 — Entity or Value Object? Ask the Right Question

Don't ask "is X inherently an Entity or a Value Object?" — ask "Does X need a tracked identity for this specific model, or is it fully described by its attributes?"

The right answer depends on what the system cares about: if identity and continuity across changes matter, it's an Entity; if only the current attribute values matter and interchangeability is fine, it's a Value Object.

This also shows that modeling is a design choice, not a fixed classification — the same concept can (and should) be modeled differently in different bounded contexts.

## Slide 32 — Aggregates

- An **Aggregate** is a cluster of associated objects (Entities and Value Objects) that are treated as a single unit for the purpose of data changes.
- Any update to the aggregate's data is made through the aggregate as a whole, ensuring the group stays internally consistent.
- The Aggregate is demarcated by a boundary which separates the objects inside from outside.
- Each Aggregate has one root, an Entity, the only accessible object from outside.
- Why this matters: the root is responsible for enforcing the aggregate's invariants

## Slide 33 — Aggregates Example (Air Travel Booking System)

- A Booking (Entity, Aggregate Root) might contain a list of Passenger Entities and several SeatAssignment Value Objects.
- External code (e.g., a payment service) never directly modifies a SeatAssignment — it must go through the Booking root, e.g., `booking.reassignSeat(passenger, newSeat)`.
- This lets Booking enforce rules like "a seat cannot be assigned to two passengers at once" or "total passengers cannot exceed aircraft capacity" — invariants that would be easy to violate if outside code could modify SeatAssignment objects directly.

## Slide 34 — Example of an Aggregate (Car)

## Slide 41 — Repositories Advantages

- They present clients with a simple model for obtaining persistent objects and maintaining their life cycle.
- They decouple application and domain design from persistence technology, multiple database strategies, or even multiple data sources.
- They communicate design decisions about object access.
- They allow easy substitutions of a dummy implementation, for use in testing.

## Slide 42 — Repositories Example (Air Travel Booking System)

- Example (Air travel booking system): `BookingRepository.findByConfirmationCode("AA123XY")` — retrieves a fully-formed Booking aggregate without the caller needing to know about joins, tables, or foreign keys.
- In tests, an `InMemoryBookingRepository` can stand in for the real database-backed one, letting you test booking logic without spinning up an actual database.

## Slide 45 — Services

- Service is used to represent behavior within a domain.
- It can group related functionalities which serves the Entities and Value objects.
- It is much better to declare service explicitly. Hence, make the operation itself easy to find, name, and reason about in the Ubiquitous Language.
- Services act as interfaces that exporses operations, which should be stateless.
- Services provide a point of connection for many objects.

*Eric Evans. Domain Driven Design. 2003*

## Slide 46 — Services (Air Travel Booking System)

- `RebookingService.rebook(booking, newFlight)` — coordinates checking seat availability, canceling the old seat, applying rebooking fees, and updating the Booking aggregate. This clearly doesn't belong on Flight or Booking alone, since it spans both.
- `FarePricingService.calculateFare(route, date, seatClass)` — computes a price using several inputs, with no natural "owner" object among Route, Plane, or Fare.

*Eric Evans. Domain Driven Design. 2003*

## Slide 47 — Factories

- Factories are used to encapsulate the knowledge necessary for object creation, and they are especially useful to create Aggregates.
- They guarantee that an object (especially an Aggregate) is created in a valid, consistent state from the very start.
- They separate "how to build it" from "how to use it."

*Eric Evans. Domain Driven Design. 2003*

## Slide 48 — Factories (Air Travel Booking System)

- `BookingFactory.createBooking(customer, flight, seatPreference)` — checks seat availability, generates a confirmation code, initializes the booking status, and assembles the full Booking aggregate (with its Passenger and SeatAssignment parts) as one atomic, valid unit — rather than leaving client code to piece it together step by step and risk creating an invalid booking.

*Eric Evans. Domain Driven Design. 2003*

## Slide 59 — Problem in a Large Project

- Multiple models are in play on any large project.
- When code based on distinct models is combined, software becomes buggy, unreliable, and difficult to understand.
- Communication among team members becomes confused.
- It is often unclear in what context a model should not be applied.

## Slide 60 — The Problem, Illustrated

- Imagine one large airline system built by several teams. Each team is really working with a different idea of what a "Flight" or "Passenger" even means, but everyone's using the same words:
  - **Booking team** thinks of a Flight as something customers search, select seats on, and pay for.
  - **Operations team** thinks of a Flight as an aircraft, crew assignment, gate, and departure/arrival schedule that must comply with safety regulations.
  - **Loyalty/Rewards team** thinks of a Flight mainly as a point-earning event tied to a Passenger's membership tier.
  - **Check-in/Airport team** thinks of a Passenger as someone who needs a boarding pass, baggage tag, and security clearance — attributes the Booking team's model doesn't even have.

## Slide 61 — The Problem, Illustrated (cont.)

Same bullets as Slide 60, with two added callouts:

- If all these teams try to share one single Flight class and one single Passenger class, that model becomes bloated with fields and logic that only matter to some teams, communication breaks down
- `Flight.status` mean 'boarding' or 'searchable for booking'

## Slide 62 — To Manage a Large Project

- Explicitly define the context within which a model applies.
- Explicitly set boundaries in terms of team organization, usage within specific parts of the application, and physical manifestations such as code bases and database schemas.
- Keep the model strictly consistent within these bounds, but don't be distracted or confused by issues outside.

## Slide 63 — Bounded Contexts (Air Travel Booking System)

| Bounded Context | Its own Flight model | Its own Passenger model | Owning team |
|---|---|---|---|
| Booking Context | Route, price, available seats, fare class | Contact info, payment method, booking history | Booking team |
| Operations/Scheduling Context | Aircraft assignment, crew roster, gate, maintenance status | (Passengers barely modeled here — just a headcount) | Ops team |
| Check-in/Boarding Context | Departure gate, boarding time, boarding status | Boarding pass, seat number, ID verification, baggage tag | Airport ops team |
| Loyalty Context | Just a reference/ID — "which flight earned these points" | Membership tier, points balance, points earned | Loyalty team |

## Slide 74 — Open Host Service

![Slide 74](png/page-74.png)

Figure: *Team 1* exposes an **OHS** box on its boundary, which *Team 2* connects to.

An Open Host Service defines **a standardized protocol or interface** that gives access to your Bounded Context as a set of services. OHS is the door.

Ask **"how do outsiders reach my context?"** → that's the OHS design question (REST API? gRPC? message queue? file feed?).

*Vernon, V. Domain-Driven Design Distilled (2016). Chapter 4: Strategic Design with Context Mapping. Pearson Education, Inc*

## Slide 75 — Published Language

![Slide 75](png/page-75.png)

Figure: *Team 1* exposes a **PL** box (with a document icon attached) that *Team 2* connects to.

- Callout: Use well-documented shared language that can express the necessary domain information as a common medium of communication
- Such a Published Language can be defined with XML Schema, JSON Schema, or a more optimal wire format, such as Protobuf or Avro.
- Ask **"what shape/vocabulary do outsiders receive when they get there?"** → that's the Published Language design question (custom schema? industry standard? versioned contract?).

*Vernon, V. Domain-Driven Design Distilled (2016). Chapter 4: Strategic Design with Context Mapping. Pearson Education, Inc*

## Slide 80 — Making Good Use of Context Mapping

![Slide 80](png/page-80.png)

Three integration styles between Bounded Contexts:

- **RPC** — a *Service Bounded Context* is described by a WSDL (which "Describes service"); a *Service Registry* "Points to description" / "Points to service"; the *Client Bounded Context* "Finds service" in the registry and calls the service with SOAP (XML).
- **RESTful** — *Service Bounded Context* ↔ *Client Bounded Context* over RESTful HTTP.
- **Messaging** — a *Publishing Bounded Context* emits a *Domain Event* to a *Messaging Mechanism*, which delivers the *Domain Event* to a *Subscribing Bounded Context*.

What a specific kind of interface would be supplied to allow you to integrate with a given *Bounded Context*?

*Vernon, V. Domain-Driven Design Distilled (2016). Chapter 4: Strategic Design with Context Mapping. Pearson Education, Inc*
